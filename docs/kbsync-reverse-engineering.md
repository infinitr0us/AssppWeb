# kbsync 算法逆向分析

> 状态:最终调用的完整差分回放通过;初始化路径与性能优化进行中。
> 本文档记录对 StoreAgent/CoreFP kbsync 生成算法的逆向工程过程、结论与移植方案。
> 复现工具链见 `frontend/tests/kbsync/`(kbsync-trace.mjs、kbsync-initprof.mjs)。

## 1. 背景与目标

`ent/download` 请求需要 `kbsync` blob(196 字节,首四字节 `00 04 00 03`),
绑定账号 DSID 与设备 GUID。当前实现(`frontend/src/apple/kbsync/`)在
Unicorn WASM 中模拟 OS X 10.9 StoreAgent 生成,单次 ~29 秒,几乎全部
耗在 StoreAgent 全局初始化。目标:移除 Unicorn,用纯 TS 实现算法并优化速度。

## 2. 方法论:动态跟踪优先于静态反编译

静态分析的已知障碍(见 `frontend/src/apple/kbsync/README.md`):

- CoreFP `_X46O5IeS` 符号覆盖 0x1735d0..0x66dbc0,其后还有一个 ~4.9MB
  的函数(0x66dbc0 起),使用**重叠指令流**混淆 —— Ghidra 报告不可恢复。
- nicolo.dev 与看雪的分析确认 FairPlay 使用控制流扁平化 + 自定义字节码
  VM + 按魔法常量解析导入等混淆。

本次采用**执行流驱动**的方法绕过混淆:

1. 用仓库自带 Unicorn harness 加全范围 code hook,记录 kbsync 最终调用
   执行的每条指令地址(`tests/kbsync/kbsync-trace.mjs`)。
2. 从每个基本块的**精确入口地址**反汇编(objdump `--start-address`),
   绕过重叠指令流 —— 线性反汇编在该区域不是指令边界的地址,从真实入口
   解码即为实际执行的流。
3. 对初始化阶段做轻量剖析:计数回调 + 分支目标位图 + 按阶段快照
   (`tests/kbsync/kbsync-initprof.mjs`)。
4. 用硬件 ID A/B 对照实验量化设备绑定数据。
5. 差分回放验证 TS 实现(最终调用通过,初始化路径继续验证)。

## 3. 关键测量结果

### 3.1 整体规模

| 阶段                      | 指令数                  | 唯一基本块入口  | 耗时                 |
| ------------------------- | ----------------------- | --------------- | -------------------- |
| StoreAgent 全局初始化     | 1,136,293,133(~11.4 亿) | 3,264(早期剖析) | Unicorn ~29s         |
| kbsync 最终调用(完整捕获) | 5,061,098               | 2,177           | TS 带逐块差分约 2–4s |

- 最终调用完整捕获含 CoreFP 4,925,925 条、storeagent 135,107 条、shim 66 条;
  61,122 个不同指令地址,158,839 次非连续块入口。
- 早期的 **1,491,313 条 / 452 块**来自漏掉初始化缓存块的 hook,不能当作完整规模。
  同理,“storeagent 仅入口壳”的推断不成立。缓存盲区见 §5.1。
- 初始化 ~29% 的指令(3.28 亿)集中在 `CoreFP+0x1e5000` 一页,
  对应 `CoreFP.icxs` 解密内循环(早期剖析结果)。

### 3.2 指令集覆盖面

完整回放实际执行了以下主要类别:

- 整数 mov/lea/ALU、8/32/64 位乘除、移位与旋转、SHRD、条件跳转、
  条件移动、栈操作、字符串操作、`rdtsc`。
- **不能把 64 位值统一当作 Number**:混淆代码使用任意 64 位常量编码指针,
  `lea` 也用作模 2⁶⁴ 加法。地址最终很小,不代表中间值小。
- **存在 SSE**:如 `storeagent+0xcf19f` 的 `xorps xmm0,xmm0` 与紧接的
  `movaps` 栈清零。当前实现 XMM 按字节存储,覆盖 XORPS/MOVAPS 的所需形式。
  早期“纯整数、无 SSE”来自不完整跟踪,现已撤回。
- 初始化额外遇到 `BT` 的立即数和寄存器形式,已补齐位测试/置位/复位/翻转族。
- x87 层仍是早期近似实现。某份回放通过只说明该执行路径的可见结果相符,
  不代表所有 x87、SSE 或任意 x86-64 程序都已正确支持。

### 3.3 混淆模式(已在汇编中确认)

1. **按魔法常量解析导入**:
   ```asm
   movl $0x2223D1AE, %edi      ; 函数句柄
   callq 0x1000e9420           ; 解析器:纯算术哈希 → 指针表槽位
   callq *%rax                 ; 真实函数
   ```
   解析器为可移植的确定性算术(移位/乘法/取模/查表),不依赖运行时状态。
2. **重叠指令流**:磁盘上线性反汇编与执行流错位;从执行入口反汇编即恢复。
3. **负偏移表索引**:`leal -0x62de407f(%rdx), %esi` 之类的常量使得
   state+const 模 2³² 回绕到小的表下标(表在 0xe1b900 等)。
4. x87/系统指令噪声插入。

### 3.4 加密核心(热循环,CoreFP+0x50e3a0,迭代 14,256 次)

表驱动 ARX 混合函数,每轮(伪代码,全部 32 位):

```
edx = state
t0  = TABLE[(edx + 0x9D21BF81) mod 2^32]          ; 4 字节表 @CoreFP+0xe1b900
t1  = TABLE[(edx + 0x9D21BF82) mod 2^32]
t2  = TABLE[(edx + 0x9D21BE9E) mod 2^32]
v   = ((t1 & 0x7FFFFFFE) | (t0 & 0x80000000)) >> 1
v  ^= t2
v   = v*2 - (v*2 & 0x7AD21DF2) + 0x3D690EF9        ; 掩码加法混合
v  ^= local[(t1 & 1)*4 ...]                        ; -0x20e8(%rbp,%rbx,4),rbx=t1&1
state = ...                                        ; 存回 -0x2538(%rbp)
```

表常量、循环次数、外层驱动(0x50e4eb ×36 / 0x50e6be ×108 / 0x50e729 ×144
等)均已在 `blocks2-*.asm` 反汇编中固定,可完整还原。

### 3.5 状态与设备绑定(核心架构发现)

初始化把 `CoreFP.icxs`(5,288,352 B)解密进 CoreFP `__common` 段
(0xe198e0..0x5e5a000,~5.3MB,init 后 99% 非零)。

**两个不同硬件 ID 的初始化结果仅差 15,514 字节(13 个区间)+ 堆上
~2.7KB**,即:

- ~5.3MB 解密状态与**设备无关**(纯 icxs 的函数);
- 设备绑定只通过 ~18KB 数据进入:
  - `CoreFP+0xe1b900..0xe1c2c0`(2,496B,热循环表 —— **init 期间被改写**,
    磁盘字节与内存不同)
  - `CoreFP+0x1066f10..0x1067eb0`(`__common` 内 4,000B)
  - `CoreFP+0xe11418..0x13804`(9 个区间,~10KB)
  - 少量指针值 + 堆对象
- 堆在 init 后仅使用 ~192KB。
- init 期间 CoreFP 六个导出函数被进入 5 次(fdjkDSAFjklaf2s×2、
  WIn9UJ86JKdV4dM、X46O5IeS ≈9s/12s、YlCJ3lg);设备增量表在 phase-05
  之后(StoreAgent 尾链)才完成写入。

## 4. TS 实现方案

依据上述测量,采取**执行 Apple 代码的纯 TS x86-64 子集解释器**路线
(`frontend/src/apple/kbsync/tsx86.ts`),而非手工重写 3,700 个块的语义:

- 解释器实现实测指令子集(整数 + 字符串 + rep + x87 噪声 + rdtsc),
  与 vendored Unicorn glue 同接口(memMap/memWrite/regRead/onCodeHook…),
  因此 `machImage.ts`(Mach-O 装载/重定位)与 `shims.ts`(libc/CF shim)
  **零改动复用**。
- 内存模型:少量连续区段 + 单槽查找缓存;寄存器为 32 位低/高半对,
  64 位数据通路使用 BigInt,32 位计算继续用 Number。
  有效地址先以 BigInt 做模运算,最后才转 Number 索引内存。
- rdtsc 由可注入计数器提供;arc4random/gettimeofday 注入确定性实现以
  支持差分测试。
- 性能路径:v1 逐指令解释;v2 基本块 → JS 闭包翻译缓存(块链接),
  目标 init ~5–15s、最终调用 <50ms;尚未达到,不能作为当前性能承诺。

### 4.1 验证方案(差分回放)

1. Unicorn 侧回放捕获:完整内存快照(含栈)、逐块指令序列、rdtsc 返回
   值序列、确定性 shim(种子化 arc4random、固定时钟)。
2. TS 解释器从捕获的初始化后内存重放最终调用(旧捕获只保存部分入口寄存器):
   - 比较**块地址序列**(任何寄存器语义错误 → 控制流分歧);
   - 比较最终 **196 字节输出**;
   - 比较 dispose 后**非栈内存**与 shim 分配器/随机数状态。
   - 旧捕获缺失完整入口寄存器和 shim 内存,不声称逐字节验证全部 CPU 状态或栈。
3. 全流程(init+final)纯 TS 跑通后做格式校验(长度 196、`00 04 00 03`),
   并与 Unicorn 输出做结构对比(rdtsc/随机源导致的字节级差异属预期,
   有效性最终由 Apple 服务器判定)。

## 5. 差分回放验证(核心工程方法)

### 5.1 关键基础设施发现:Unicorn hook 的缓存盲区

**打了补丁的 TCI-wasm 构建不会为 init 期间已翻译缓存的代码块重新检查后注册的
code hook。** 若在 init 之后才注册 images 范围的 hook,最终调用里有 70% 的指令
(3.56M/5.05M,全部落在 init 已执行过的块里,如导入解析器 0xe9420)不会触发
hook——跟踪会静默漏录。修正:hook 必须在 init 之前注册(代价:init 从 29s 变
~87s,仅研究用)。

### 5.2 确定性回放协议

- 确定性 shim:种子化 LCG 的 `_arc4random`、固定时钟的 `_gettimeofday`
  (shims.json 序列化布局与堆分配器状态,回放侧原样恢复);
- rdtsc:**参与控制流**(不同运行指令数 4.99M~5.05M 不等),捕获端按字节检测
  `0f 31` 并在 hook 间隙录制 RAX/RDX,回放端按序消费(1334~495 次/运行);
- unicorn 的 regRead 以 double 返回 64 位寄存器:≥2^53 的值(如 0xFFFFFFFFFFFFFFF3)
  舍入为 2^64。回放按同样的无符号 f64 数值比较,不做“任意负数等于 2^64”
  的宽松容差。指令级单测把完整寄存器写入内存再逐字节对照,避免舍入掩盖错误。

### 5.3 已修复的解释器 bug(差分回放与指令级对照定位)

1. `immS` 的 `1 << 31` 符号扩展溢出(32 位 disp 全错)
2. RIP 相对寻址缺失(mod=0/rm=5)
3. RIP 相对 disp32 未符号扩展(+2^40 类地址误差)
4. `48 69` 三操作数 imulq 按 32 位计算
5. 64 位移位计数掩码错误(`& 31` 应为 `& 63`)
6. `movslq` 符号扩展加 2^32 而非 2^64(2^64 往返在 double 中不可表示)
7. getQ/setQ 拆分对负数/大值精度错误(floor 拆分 + 负数有符号表示)
8. `wrap64` 的 +2^64 往返破坏精度(200 → 0)
9. 条件码表 5/6/7 错位(JNE 写成 `zf|cf`)
10. 减法 CF 按加法进位计算(借位语义,`cmp 0,5` 型比较出错)
11. 64 位 AND/OR/XOR/TEST 用 JS 位运算符被截成 int32(BigInt 修复)
12. REX 前缀下字节寄存器映射错误(dil 读成 bh)
13. push/pop 默认操作数宽度(长模式为 64 位)
14. `ff /2,/4,/6`(间接 call/jmp/push)默认 64 位操作数
15. 指令长度解码器:ALU 立即数形式误判有 ModRM;`c1` 移位 imm 长度错误

每个修复使匹配前缀显著推进:8 → 17 → 71 → 78 → 190 → 244 → 847 → 1045 →
28,384 → 106,665 → 119,216 → 130,550 → 4,493,260 → **5,061,098(全部)**。

本轮补齐/修复:

16. `toSigned` 的 JS 位移溢出及负立即数被二次符号扩展
17. 64 位搬运/ALU/LEA/乘除/移位必须保留所有位,包含 128 位乘积与被除数
18. 16 位寄存器写入必须保留其余高位;8 位 MUL/DIV 使用 AX,不能破坏 RDX
19. RIP 相对地址从完整指令末尾计算(含立即数);SIB 的 REX.X 可选 R12
20. LEA 写 32 位目标必须先截断,不能把 64 位回绕结果转 double 后再截断
21. ROL/ROR/RCL/RCR 编码映射、SHL 进位与 SHR/SAR 的符号/位宽语义
22. 新增 XORPS/MOVAPS、SHLD/SHRD、BT/BTS/BTR/BTC 实测所需形式
23. 近条件跳转没有 ModRM;15 字节 NOP 的前缀扫描不能限于 6 字节
24. PUSH 立即数、CDQE/CQO 的符号扩展;执行次数/超时/停止与 RDTSC 耗尽检查
25. CPUID leaf 0/1 返回值改为 vendored Unicorn 的 Haswell 配置,不再返回零占位

### 5.5 初始化的独立 lockstep 与映射内存陷阱

新增 `kbsync-init-diff.mjs`,从真实生产 loader/shim/StoreAgent 调用序列开始:

- Unicorn 负责提供真实 RDTSC;shim 随机数/时钟只调用一次,向两个引擎写入相同结果;
- 每个指令地址与长度比较,每次写入在下一条指令前比较实际内存字节;
- 每个块入口比较全部 16 个 GPR 的完整 64 位;
- 用 `regRead(RAX)` 的舍入值加 `regRead(EAX)` 的精确低 32 位还原高位:
  `high = round((rounded - low) / 2^32)`,不需要修改 WASM glue;
- 每次 guest 调用前后比较所有映射区,包含栈和 shim 区。

新的前置内存断言发现:vendored Unicorn WASM 的新映射可能重用未清零 RAM。
最小实验中,写入 `0xab` 后释放再映射 128KiB,有 90,381 个非零字节;
实际 loader 在第一条 guest 指令前就已出现 CommerceCore/BSS 内存差异。
因此之前约 8,484 万指令处的 SETNE/全局变量差异不能归因于 TS 指令语义。

lockstep harness 现在显式清零参考引擎的映射,与 TS 的零填充内存保持一致,
并在每次调用前断言相等。独立运行显式清零的 Unicorn 完整 init+final 成功,
返回 196 字节及正确前缀,耗时约 27 秒。生产 Unicorn wrapper 本轮未改动。

```bash
KBSYNC_ASSET_DIR=/tmp/asspp-sap/sap-assets \
  node --import ./backend/node_modules/tsx/dist/loader.mjs frontend/tests/kbsync/kbsync-init-diff.mjs
```

`DIFF_LO/DIFF_HI` 可对指定指令地址区间逐指令检查寄存器;
`WATCH_ADDRESS` 可在块入口检查某个 8 字节内存位置。此验证比单引擎慢,
有 30 分钟的每次调用上限,不能作为解释器性能基准。

独立 TS 离线生成已通过(同一设备 ID、合成 DSID `12345678901`):
默认递增 RDTSC 的初始化执行 1,136,591,591 条指令,耗时 436.3 秒;
最终调用 5,021,314 条指令,耗时 1.83 秒,返回 196 字节及正确前缀。
使用 `performance.now() * 1e6` 作为 RDTSC 时,初始化执行 1,136,577,973 条指令,
耗时 437.5 秒;最终调用约 502 万条,耗时 1.95 秒,返回 196 字节及前缀
`00 04 00 03`。这些时间来自与其他诊断进程并行的运行,不是隔离性能基准。
独立生成成功不等于逐字节等价或 Apple 服务接受;这两项分别需要 lockstep 和在线验证。
离线 `kbsync-live.mjs` 的 TS 模式将单次 guest 调用上限提高到 20 分钟,
生产 worker 的 5 分钟上限保持不变。

首次完整 lockstep 在第 1,136,219,817 条指令、CoreFP `+0x48c967` 发现 RAX 差异。
该块内 `+0x48c703` 执行 CPUID leaf 1:原解释器返回全零,参考值 EAX 为 `0x306c4`。
已按参考引擎补齐 leaf 0/1 的四个输出寄存器并增加独立指令单测;
其他未实现的叶号明确报错,避免静默使用占位值。上述独立运行耗时是修复前基线。
修复后,仓库内 `KBSYNC_ENGINE=ts` 离线脚本完整运行成功,总耗时 419.5 秒,
输出 196 字节且前缀正确。独立原生参考运行在所有载入镜像的 46 个 `0f a2`
候选地址预注册 hook,确认该路径只执行上述 leaf 1 查询。

### 5.6 块级 JIT

`tsx86-jit.ts` 将已解码的整数基本块编译为 JavaScript 函数;生成源码仅包含固定模板
和 guest 指令的数值操作数。64 位数据保留为两个 uint32,低位乘法用 `Math.imul`
与精确高半积计算,不将任意 qword 转成 Number。RDTSC、x87/SSE 及其他未编译指令
回到原解释器,未改动 Apple 协议、生产 worker 或资产交付。

保留的优化:

- 寄存器局部变量,仅回写修改过的半寄存器;故障时也通过 finally 回写状态。
- 保守删除块内会被覆盖的 flags 写入,在内存故障/写入及块出口保留可观察状态。
- 每个访存点缓存 DataView 和映射范围;对代码页的写入使相关块失效。
- 通过已缓存的后继块批量执行,每约 4096 条指令返回调度器检查超时。
- 冷代码先解释执行三次,再编译重复访问的地址,减少首次调用的编译成本。

曾尝试将多块合成为一个大函数,但初始化退化到约 9–12 秒,已移除。
所有诊断完成后,以 5 个独立 Node 进程重新计时,完整 guest 调用包含 JIT 编译:

| 阶段   | 中位数   | 最小–最大       | 目标  |
| ------ | -------- | --------------- | ----- |
| 初始化 | 5.872 秒 | 5.844–6.001 秒  | 5 秒  |
| 生成   | 236.59ms | 235.90–239.39ms | <50ms |

资产从本地读取,不包含下载时间;这些结果不是浏览器或生产性能承诺。
两个目标尚未达到。初始化编译耗时中位数 544.14ms,最终调用新增编译 79.46ms;
生成阶段的执行时间本身也仍超过 50ms。

验证分为三条路径,避免观察器关闭优化后造成虚假的覆盖:

1. 默认 JIT replay 保留每条 PC、捕获块寄存器、RDTSC、输出、非栈内存和 shim 对照。
   两个 DSID 的 5,061,098 / 4,999,572 条指令均通过。
2. `REPLAY_BENCH=1` 真正运行优化路径,仍断言输出、内存、shim 状态和 RDTSC 消耗一致;
   不声称做逐指令寄存器对照。两个 DSID 均通过。
3. `KBSYNC_ENGINE=jit kbsync-init-diff.mjs` 在优化执行批次与 Unicorn 间对齐:
   每条参考 PC/长度必须匹配,批次出口检查全部 16 个精确 64 位 GPR 及所有写入区域,
   调用返回检查全部映射内存(含栈/shim)。同一批次重叠写入检查最终字节值。
   每个块按实际执行数量记录,代码写入导致提前退出时不会记录未执行的后半块。
   原始逐指令解释器 lockstep 保留。

优化模式全流程复核已通过(2026-10-25):初始化 1,136,517,410 条指令,
最终调用 5,019,618 条,释放 47 条;合计 1,141,537,075 条指令和 4,634,853 个批次边界。
调用返回的全部映射内存、shim 状态和 196 字节输出一致。故意将首个编译块的 RAX
增加 1,验证在第 481 条指令报错退出,确认优化模式不会绕过对照。

全前端 555 项测试通过,包括 381 项解释器/JIT 测试。新增覆盖热循环、冷编译阈值、
代码自修改、hook/观察器修改和停止、块中间 until、指令数量限制、重新映射、写观察器
以及访存故障后的精确状态;类型检查和 Vite 构建通过。

### 5.8 共享基址访存与热循环 region 合并

对 5.6 的块级 JIT 做了两层优化(2026-10-25):

**诊断。** 初始化 11.4 亿条指令被拆成 1.16 亿次块调用,平均每块 9.8 条;
CPU profile 中生成代码占 52%、调度器占 25%、编译占 10%,解释器回退不到 0.1%。
80% 的指令集中在两个循环:CoreFP icxs 解密内循环(`+0x1e51b0` 三个块,间接跳转)
和 storeagent 控制流扁平化循环(`+0x107c72` 一带约 20 个 1–8 条指令的小块)。
瓶颈是每块固定的进出开销,不是指令语义。

**共享基址访存点。** 同一个基址寄存器的无索引操作数(如 `-0x2490(%rbp)`)在块内
共享一次映射检查:第一次使用该寄存器时对所有位移覆盖的区间做一次检查,寄存器被写入
后才重新推导;每次访存变成缓存 `DataView` 上的一次带边界检查的读写。区间内任何
一处未映射都在首次使用处报告故障;`memMap` 会合并相邻映射,保证连续的已映射区间
只有一个后备视图。带索引的操作数保留精确的模 2⁶⁴ 寻址和逐次检查:
CoreFP `+0xd1f3ee` 的 `movq (%rcx,%r15)` 依赖回绕访问堆。

**Region。** 执行 50 万次的块与其热后继合并编译成一个函数
(`for(;;){switch(pc){...}}`),寄存器在块之间始终留在局部变量里。成员按执行次数
最优先纳入,受生成源码 18,000 字符预算限制:超过约 40KB 源码后 V8 不再用顶层优化
编译器,较低层级跑这类代码只有 100–150M 指令/秒,反而比单块更慢。间接跳转先比较
观测到的后继,再对全部成员做二分比较树。频繁退出到非成员的 region 最多围绕其
高频出口重建两次;出口统计跳过每 8,192 条指令一次的预算返回(供调度器检查超时)。
指令数受限的运行不使用 region;`until` 落在成员内的 region 不会被使用;设置
`executionLog` 时 region 逐成员记录,差分 harness 仍能看到每个执行过的块。
批次循环移到 `runBatch`,region 像块一样参与 next0/next1 链接,退出不再查 Map。

**踩过的坑(都有测量支撑):**

- 两个 region 各覆盖半个循环会互相"乒乓",每次迭代进出两次,调度器开销吃掉全部收益;
- 把 region 做大(240–320 条指令,50–64KB 源码)后 V8 只用 Maglev 或 baseline,
  速度降到 100–150M 指令/秒;
- 按出口统计反复"生长"region,每次重建都是冷代码,数百次重建后总时间反而翻倍;
- region 阈值过低(1 万次)会建出 200 多个 region,每个都要付出 V8 解析、惰性编译
  和分层预热的成本;提高到 50 万次只剩 20 多个,初始化少了约 0.85 秒。

**结果。** 同一会话、同一台机器(此时已比 5.6 节测量时降频)上三次独立运行:

| 阶段   | 原块级 JIT     | 共享访存点 + region | 目标  |
| ------ | -------------- | ------------------- | ----- |
| 初始化 | 6,410–6,582 ms | 4,031–4,042 ms      | 5 秒  |
| 生成   | 262–267 ms     | 229–231 ms          | <50ms |

21–25 个 region 承担 8.43 亿条初始化指令,整体 680M 指令/秒;storeagent 状态机
循环作为单个 region 跑到约 890M 指令/秒。剩余时间约为:region 1.2 秒,生成块源码
0.45 秒,V8 解析/惰性编译/预热 4,450 个块函数约 1 秒,其余在单块执行和调度。
生成阶段仍需现编约 560 个新块并冷启动运行,50ms 目标未达成。
单元测试新增共享区间故障位置、相邻映射合并、热循环 region 与解释器对照、
指令预算下不建 region、成员日志、`until` 落在成员内、成员写入其他已编译代码页
七个用例(共 397 项通过)。

改动之后重跑了优化路径的全流程差分(`KBSYNC_ENGINE=jit kbsync-init-diff.mjs`,
参考引擎为历史 Unicorn 版本),通过:初始化 1,136,460,421 条指令,加最终调用与释放
共 1,141,519,289 条;4,321,395 个批次边界的全部 16 个精确 64 位 GPR 与写入字节、
每次调用返回时的全部映射内存(含栈/shim 区)及 196 字节输出均一致,耗时 265 秒。
用同样的驱动方式(开启 `executionLog`、每批次 `emuStop`)去掉参考引擎重放一次:
建出 25 个 region,region 执行 166 万次、覆盖 8.34 亿条指令、产生 9,030 万条成员日志,
说明这次对照覆盖了 region 路径而不只是单块。
